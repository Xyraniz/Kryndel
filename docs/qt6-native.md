# Native Qt 6 bindings for Kryndel

## Decision

The Qt integration is native: Kryndel programs must not need CPython or PyQt6 at run time. The implementation will bind to Qt 6's C++ libraries and expose a Kryndel API with coverage matching the public Qt surface wrapped by a pinned PyQt6 release. Python-only conveniences are represented with Kryndel types and call semantics; this is not a Python compatibility runtime.

The compatibility baseline is PyQt 6.11.0 and Qt 6.11. PyQt6's separately released 3D, Charts, DataVisualization, Graphs, NetworkAuth, and WebEngine packages are included in the full-coverage target. The current native prototype has been built against Qt 6.11.0, but it does not implement the full target.

Qt remains an optional application dependency. The Kryndel compiler and its non-GUI applications stay independent of Qt.

## Scope of complete support

Calling the integration complete requires an inventory generated from the selected PyQt6 release and matching coverage for its public modules, classes, constructors, methods, overloads, enums, flags, properties, signals, slots, and value conversions. The binding must also preserve QObject ownership, destruction, thread affinity, queued delivery, and the Qt event loop.

A small set of Qt Widgets is only an early milestone. It does not satisfy full PyQt6 coverage. Coverage gaps must remain visible in the generated inventory instead of being described as supported.

## Runtime architecture

Kryndel's release runtime is pure Go and is built with CGO disabled. Keep that compiler/runtime artifact independent of Qt and avoid linking the compiler to Qt. A separate native adapter can link selected Qt modules and expose stable C-ABI entry points to the Kryndel interpreter.

Kryndel's current FFI supports integer and opaque-pointer C signatures. C++ classes, overloaded methods, Qt value types, and callbacks cannot be called safely by exposing Qt's C++ symbols directly. The adapter and generated binding layer must provide typed wrappers, stable handles, checked argument conversion, deterministic cleanup, and event delivery on the GUI thread.

QObject reflection can help with runtime properties, invokable methods, and signals, but it does not describe every public C++ method or non-QObject type. Reflection alone is not a complete binding generator. Full coverage needs generated wrappers from authoritative Qt API metadata plus explicit handling for types that cannot be represented generically.

## Implementation status

The current `packages/qt6` directory is an early native prototype, not complete PyQt6 support. It builds one Qt 6.11 C ABI adapter with 45 required base modules from the PyQt module inventory linked, plus a Kryndel package that exchanges bounded JSON requests with that adapter. CMake also detects and links ActiveQt on Windows and Qt WebEngine components when installed. Each module's generated sources are compiled in separate C++ translation units because Qt Charts, Qt Graphs, and Qt Data Visualization reuse C++ class names. The combined MinGW adapter still reports duplicate RTTI sections for `QAbstractSeries` from Qt Charts and Qt Graphs, so simultaneous runtime type behavior for those modules is not validated; separate module adapter boundaries or an equivalent isolation strategy are required before claiming support for both together. The adapter has explicit partial constructors for 94 classes, generated default or standard-parent constructors for 1,256 candidate classes, and runtime discovery for public constructors registered with Qt's meta-object system. A SIP-based C++ generator now adds 944 argument-constructor variants in 61 generated shards, including separately distributed PyQt add-ons for QObject-derived classes with supported argument conversions. Colliding constructor names require a module-qualified name, for example `QtCharts.QChart`. `constructors(runtime)` reports the actual constructor names compiled into the adapter. The adapter reads and writes QObject properties, invokes public meta-object slots and invokable methods, captures selected signals, and reports QObject meta-object metadata through `describe`. Enum arguments accept registered Qt key names or integer values. It includes direct operations for common widget composition, basic `QIODevice` I/O, `QSettings`, `QFileSystemWatcher`, QProcess output, selected Qt Network calls, ActiveX controls on Windows, graphics scenes, and text documents, plus converters for a small set of Qt value types.

The generated [API inventory](../packages/qt6/api_inventory.json) covers 52 modules, 1,444 classes, 2,452 documented constructor signatures, 23,529 method signatures, 2,860 signal signatures, 1,137 enum declarations, and 9,892 documented enum values from the pinned PyQt 6.11.0 documentation. This build links the 45 base modules and optional ActiveQt; the three WebEngine components are absent from the selected kit, though CMake now links them when installed. Ninety-four classes have explicit partial native constructor bindings, 1,256 linked-or-optional module classes are default-factory candidates, and generated C++ probes 1,318 classes for QObject meta-objects. The MinGW Qt 6.11 build currently exposes 714 of those as runtime meta-objects. The probe and runtime counts describe this selected kit; they do not imply that every class is concrete, instantiable, or matches PyQt constructors. The signature and enum inventory helps plan and measure the work; it does not mean those APIs have native implementations.

The current API does not bind every public Qt module, class, constructor, C++ method, overload, value type, enum, or flag. It now handles default-constructible linked `Q_GADGET` types through their reflected properties and invokable methods, in addition to selected geometry, vector, image, regular-expression, UUID, color, date/time, URL, font, key sequence, byte-array, and enum conversions. Some constructors requiring arguments can be discovered if Qt marks them public and `Q_INVOKABLE`; most ordinary constructors and Qt value types still need generated bindings. ActiveQt currently has direct wrappers for a subset of QAxBase/QAxObject/QAxWidget APIs. WebEngine component detection, factory generation, and supported SIP wrappers are in place, but complete WebEngine API coverage, callbacks/slots implemented in Kryndel, moving QObjects between threads or queued-delivery semantics, and platform deployment tooling are still missing. The Kryndel package pins its runtime goroutine to one OS thread while the Qt session is open. `describe` reflects Qt meta-object data only; it must not be used as a claim of complete public C++ API coverage.

The SIP-based direct-method generator now emits 10,048 native C++ QObject method wrappers across 48 modules and 5,963 ordinary value method wrappers in 75 generated shards. It also emits 944 QObject argument-constructor variants in 61 generated shards and 1,168 ordinary Qt value constructor variants in 73 generated shards. Value methods were generated for 455 non-QObject classes; the runtime advertises only values that are copyable and registered with `QMetaType`. Passing a Qt value as a method argument additionally requires default construction for `QVariant` extraction. The Kryndel API exposes generated value constructors through `value_new_args`, with direct value calls through `value_call`; for example, a Kryndel program can create a `QDate` from year, month, and day integers, then call `year()`. Constructor wrappers cover public declarations with supported native JSON conversions; Qt parent handles use QWidget, QWindow, QLayout, Qt 3D QNode, or QObject ownership rules. The generated method surface includes static methods through `call_static(runtime, class_name, signature, args_json)` as well as QObject instance methods and methods on ordinary Qt values. It covers selected primitives, converted Qt values such as `QGeoCoordinate`, `QHostAddress`, and `QNetworkRequest`, signed and unsigned 64-bit integers, `QVariant` and JSON values, variant maps and hashes, string maps, enum and flag types, QObject handles, and supported Qt lists. PyQt documentation's `Any` type is treated as a `QVariant` at this boundary. Map values cross the API as JSON objects; QVariant maps preserve JSON-compatible values and string maps require string values. Values without a JSON conversion can cross the API as typed `value_id` handles and use generated `value_call` methods. 64-bit values use JSON numbers up to 9,007,199,254,740,991 and decimal strings above that range to avoid precision loss. These counts are not complete PyQt coverage: overloads whose types lack a native converter are excluded, property reflection still applies only to Qt gadgets, and generated WebEngine wrappers are guarded but not compiled or runtime-validated with this kit.

The adapter links the 45 required modules selected in `native/CMakeLists.txt`, including Qt Test because it uses `QSignalSpy` for signal capture, plus optional components available in the selected kit. The 45 matching Qt module DLLs in the inspected MinGW Qt 6.11 kit total about 80 MiB on disk, before transitive runtime DLLs, the adapter, and platform or multimedia plugins. This build therefore needs the matching Qt shared libraries at runtime, even when an application uses only a subset of the modules. The native example demonstrates the prototype API only.

## Packaging

Building the optional adapter requires a Qt 6 development installation containing the selected modules, a matching C++ toolchain, and CMake. The current all-module adapter links 45 modules, so distributing that build requires their Qt runtime libraries plus the needed platform plugins. A selectable module build and deployment manifest are still needed to produce smaller app-specific bundles.

Qt modules have different license availability. Audit the selected modules before redistribution, and retain Qt's deployment metadata, notices, and relinking requirements for the chosen license. The Kryndel CLI release must continue to work without Qt installed.

## Completion gates

- Extend the generated module/class index into a reproducible constructor, method, overload, enum, flag, property, signal, slot, and value-type inventory for PyQt6 6.11.0 / Qt 6.11. (Constructors, methods, signals, enums, and enum values are inventoried; flag classification, properties, and full value-type coverage still need static coverage. Native direct wrappers currently cover 10,048 QObject and 5,963 ordinary value method overloads, with value methods generated for 455 classes.)
- Isolate modules that export conflicting global C++ class names, including Qt Charts and Qt Graphs, then verify their simultaneous runtime behavior. Complete WebEngine and all public class/API bindings for every linked module. ActiveQt and WebEngine components are now conditionally linked when available.
- Preserve event-loop behavior, signal/slot connections, object ownership, overload selection, enum/flag conversions, and error reporting across the Kryndel boundary.
- Build the optional adapter for Kryndel's supported desktop targets and verify runtime deployment contains only required Qt modules and plugins.
- Publish the Kryndel package/API reference and a native GUI application example with the complete coverage inventory.
